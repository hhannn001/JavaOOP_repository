# 코드 방탈출 게임 기획서

## 1. 프로젝트 개요

**프로젝트 제목:** 코딩 학습용 방탈출 게임 — CODE ROOM(가제)

**구현 환경:** Java Swing 기반 데스크톱 앱

**개발 기간:** 3주 내 MVP 완성 후 QA 및 수정

Java 코드의 실행 결과를 추리하여 잠금 장치를 풀고 방을 탈출하는 2D 학습 게임을 제작한다. 사용자는 로그인한 뒤 방탈출 포스터 형태의 목록에서 맵을 선택한다. 방 안에서 코드가 적힌 종이를 모으고, 출력값을 장치에 입력하여 다음 단서와 열쇠를 얻는다.

대상은 Java 기초 문법을 배운 입문자다. 배열과 반복문 등을 눈으로 따라가며 코드의 실행 순서를 이해하는 데 초점을 둔다. 기존 HTML 프로토타입은 게임 화면과 상호작용의 참고 자료로 사용한다.

## 2. 프로젝트 목표

- 로그인부터 맵 선택, 퍼즐 풀이, 탈출까지 이어지는 게임 1개를 3주 안에 완성한다.
- 코드의 출력값과 잠금 장치의 답을 연결하여 기초 문법을 자연스럽게 복습하게 한다.
- 방이 화면을 가득 채우는 구성과 단서 수집으로 방탈출 게임의 몰입감을 만든다.
- 기능별로 역할을 나누고, QA에서 발견한 진행 오류를 우선 수정한다.

## 3. 화면 흐름

**로그인 → 맵 선택 → 게임 진행 → 탈출 결과 → 맵 선택**

| 화면 | 구성 및 동작 |
| --- | --- |
| 로그인 | 아이디·비밀번호 입력, 로그인 버튼. 인증 성공 시 맵 선택으로 이동하고 실패 시 안내한다. |
| 맵 선택 | 방탈출 포스터를 나란히 배치한다. 포스터에 맵 이름·학습 주제·난이도·클리어 여부를 표시하고, 선택하면 게임을 시작한다. 로그아웃도 이 화면에서 제공한다. |
| 게임 진행 | 방이 게임 영역 전체를 채운다. 방의 물건을 클릭해 조사하고, 왼쪽에 손에 든 코드 종이와 하단 인벤토리를 표시한다. |
| 탈출 결과 | 게임 위에 탈출 성공과 소요 시간을 표시한다. 다시 플레이하거나 맵 선택으로 돌아갈 수 있다. |

별도의 대시보드는 만들지 않는다. 학습 결과는 맵 선택창의 클리어 표시와 최고 기록으로 확인한다.

### 맵 선택창 예시

| 포스터 제목 | 학습 주제 | MVP 상태 |
| --- | --- | --- |
| 마지막 컴파일 — 잠긴 서재 | 배열, 반복문, 출력 | 플레이 가능 |
| 사라진 연구 기록 | 조건문 | 준비 중 |
| 멈춰버린 기계실 | 문자열 | 준비 중 |

포스터는 방탈출 테마를 보여주는 이미지와 짧은 소개로 구성한다. MVP는 서재 1개만 실제로 구현하며, 나머지는 확장 방향을 보여주는 비활성 포스터다. 준비 중인 맵은 시작할 수 없다.

## 4. 게임 진행 방식

| 순서 | 사용자 행동 | 결과 |
| --- | --- | --- |
| 1 | 입장 시 받은 첫 종이의 Java 코드를 읽는다. | 네 자리 출력값을 추리한다. |
| 2 | 서랍장의 숫자 잠금 장치에 `2312`를 입력한다. | 서랍이 열리고 두 번째 종이를 얻는다. |
| 3 | 새 종이에 적힌 2차원 배열 코드를 읽는다. | 세 줄의 출력값 `423 / 312 / 133`을 추리한다. |
| 4 | 벽의 3×3 다이얼에 각 숫자를 입력한다. | 작은 금고가 열리고 황동 열쇠를 얻는다. |
| 5 | 인벤토리에서 열쇠를 선택하고 출입문을 누른다. | 탈출에 성공하고 기록을 저장한다. |

위 정답은 기획·검증용이며, 플레이 화면에서는 코드와 힌트만 제공한다.

- **단서:** 종이마다 답의 모양을 표시해 네 자리 암호와 3×3 다이얼 중 어디에 입력할지 알 수 있게 한다.
- **인벤토리:** 얻은 종이와 열쇠를 보관한다. 아이템을 선택하면 왼쪽에 든 단서가 바뀌며, 종이는 접었다가 다시 펼칠 수 있다.
- **정답 판정:** 준비된 Java 코드를 읽고 결과를 입력하는 방식이다. 앱에서 Java 코드를 직접 작성하거나 실행하지 않는다.
- **재시도:** 오답은 안내만 표시하고 횟수 제한 없이 다시 입력하게 한다. 막히면 준비된 힌트를 볼 수 있다.
- **진행 순서:** 서랍 → 다이얼 → 열쇠 → 문 순서로 진행한다. 이미 얻은 아이템은 중복 지급하지 않는다.
- **중도 종료:** 맵 선택으로 돌아갈 때 현재 진행이 초기화됨을 안내한다. MVP에서는 완료 기록만 저장하고 중간 이어하기는 제공하지 않는다.

## 5. MVP 범위

**포함:** 로그인, 포스터형 맵 선택, 플레이 가능한 맵 1개, 코드 퍼즐 2개, 단서·열쇠 인벤토리, 힌트, 탈출 결과, 사용자별 클리어 기록.

로그인은 미리 등록한 시연 계정 3개로 시작한다. 실제 아이디·비밀번호를 검증하고 사용자별 기록을 구분한다. 회원가입과 비밀번호 찾기는 후속 기능으로 둔다.

기존 기획의 OX·객관식 학습 화면, IDE, AI API 피드백, 상세 학습 통계는 이번 MVP에서 제외한다. 게임 흐름을 완성한 뒤 추가 맵과 함께 필요성을 검토한다.

## 6. 구현 및 역할 분담

`JFrame` 하나에 로그인·맵 선택·게임용 `JPanel`을 두고, `CardLayout`으로 전환한다. 방 배경은 패널에 그리고 클릭 영역으로 물건을 선택한다. 암호 입력과 결과 표시는 Swing 기본 컴포넌트를 사용한다.

FSD에서 의도했던 **기능별 책임 분리**만 적용한다. 처음부터 여러 계층이나 공통 인터페이스를 만들지 않고, 로그인·맵 선택·게임·저장 기능 정도로 구분한다.

| 담당 | 작업 |
| --- | --- |
| 로그인·기록 | 로그인 검증, 사용자 구분, 클리어 기록 저장 |
| 맵 선택·화면 | 포스터 목록, 화면 전환, 방 배경 및 클릭 영역 |
| 게임 로직·콘텐츠 | 코드 종이, 암호 판정, 인벤토리, 열쇠와 탈출 조건 |

인원에 따라 역할을 합친다. 개발 시작 시 사용자 ID, 맵 ID, 게임 완료 시 전달할 소요 시간만 먼저 합의한다.

저장은 **로컬 SQLite 파일 하나와 JDBC 드라이버**를 사용하는 안으로 잡는다. 별도 서버는 두지 않는다. DB 작업은 화면을 멈추지 않게 처리하고, 저장 실패 시 안내와 재시도를 제공한다. 비밀번호는 평문으로 저장하지 않고, 사용자별 salt를 적용한 비밀번호 해시로 검증한다.

## 7. 데이터 구성

초기 데이터와 예상 개수는 아래처럼 작게 시작한다. `PK`는 기본키, `FK`는 외래키다. 자료형은 SQLite 기준이며 필드는 모두 필수값으로 둔다.

| 데이터 이름 | 데이터 설명 | 예상 개수 |
| --- | --- | --- |
| 사용자 (`users`) | 로그인할 시연 계정 | 초기 3개 |
| 맵 (`maps`) | 포스터, 소개, 플레이 가능 여부 | 3개: 플레이 가능 1개 + 준비 중 2개 |
| 퍼즐 (`puzzles`) | 코드 종이, 정답, 힌트, 풀이 순서 | 서재용 2개 |
| 클리어 기록 (`clear_records`) | 사용자별 맵 완료 여부와 최고 기록 | 초기 최대 3개: 사용자 3명 × 플레이 가능한 맵 1개 |

### 주요 Attribute

| 데이터 | 속성 | 자료형 | 설명·키 |
| --- | --- | --- | --- |
| users | user_id | INTEGER | PK, 사용자 번호 |
| users | login_id | TEXT | 로그인 아이디, 중복 불가 |
| users | password_hash | TEXT | salt와 검증 설정을 포함한 비밀번호 해시 |
| maps | map_id | INTEGER | PK, 맵 번호 |
| maps | title | TEXT | 포스터에 표시할 제목 |
| maps | description | TEXT | 맵의 짧은 소개 |
| maps | topic | TEXT | 배열·반복문 등 학습 주제 |
| maps | difficulty | TEXT | 쉬움·보통·어려움 |
| maps | poster_path | TEXT | 앱에 포함된 포스터 이미지 경로 |
| maps | playable | INTEGER | 1: 플레이 가능, 0: 준비 중 |
| puzzles | puzzle_id | INTEGER | PK, 퍼즐 번호 |
| puzzles | map_id | INTEGER | FK → maps.map_id |
| puzzles | step_no | INTEGER | 풀이 순서, 서재는 1 또는 2 |
| puzzles | code | TEXT | 종이에 표시할 Java 코드 |
| puzzles | answer_type | TEXT | `DIGITS4` 또는 `GRID3X3` |
| puzzles | answer | TEXT | 정답 숫자열, 예: `2312`, `423312133` |
| puzzles | hint | TEXT | 막혔을 때 보여줄 설명 |
| clear_records | user_id | INTEGER | 복합 PK, FK → users.user_id |
| clear_records | map_id | INTEGER | 복합 PK, FK → maps.map_id |
| clear_records | best_seconds | INTEGER | 가장 짧은 탈출 시간(초), 0 이상 |

클리어 기록은 `(user_id, map_id)`당 하나만 저장한다. 첫 탈출 때 생성하고 이후 더 빠른 기록이 나오면 갱신한다. 기록이 있으면 해당 맵을 클리어한 것으로 표시한다. 퍼즐의 `(map_id, step_no)`도 중복되지 않게 한다.

네 자리 암호는 숫자 4개, 격자는 칸마다 숫자 1개를 입력받는다. 격자는 왼쪽 위부터 행 순서로 이어 붙여 정답과 비교한다. 정답을 문자열로 저장해 앞자리 `0`도 유지한다.

인벤토리와 열린 장치는 게임 실행 중 상태로만 관리한다. 서재는 **시작 / 서랍 해제 / 다이얼 해제 / 탈출 완료** 네 단계면 충분하다. 아이템·장치·개별 시도 이력 테이블은 만들지 않는다.

## 8. 개발 일정 및 완료 기준

| 기간 | 할 일 | 완료 기준 |
| --- | --- | --- |
| 1주 차 | 로그인, 포스터형 맵 선택, 화면 전환, 기본 데이터 준비 | 로그인 후 서재를 선택해 입장할 수 있다. |
| 2주 차 | 방 화면, 코드 종이, 두 잠금 장치, 인벤토리, 열쇠 구현 | 첫 단서부터 문을 열기까지 진행할 수 있다. |
| 3주 차 | 결과·기록 저장, 화면 및 콘텐츠 보완, 기능 통합 | 다시 로그인해도 클리어 여부와 최고 기록이 남는다. |
| MVP 완성 후 | QA, 오류 수정, 재검증 | 게임 진행을 막는 오류와 기록 저장 문제를 해결한다. |

QA는 로그인 성공·실패, 준비 중 맵 선택 방지, 암호의 빈 입력·오답·정답, 단서 교체, 아이템 중복 방지, 열쇠 없이 탈출 방지, 재시작 및 사용자별 기록 구분을 확인한다.

**최종 완료 기준:** 사용자가 로그인하여 맵을 고르고, 두 코드 퍼즐을 풀어 열쇠로 탈출한 뒤, 자신의 클리어 기록을 다시 확인할 수 있다.
