# PR 및 커밋 규칙

이 문서는 7명이 Java Swing 방탈출 프로젝트를 함께 개발할 때 쓰는 기본 규칙이다. 

## 1. 커밋 메시지

[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)의 기본 형식을 사용한다.

```text
type(선택적 범위): 변경 내용
```

`type` 뒤에 `: `를 쓰고, 변경 내용을 한 줄로 적는다. 변경 내용은 한국어와 영어 중 하나를 자유롭게 쓰되, 같은 PR 안에서는 한 언어를 유지한다. 범위는 변경한 기능을 분명하게 할 때만 적는다.

| type | 사용할 때 | 예시 |
| --- | --- | --- |
| `feat` | 사용자에게 보이는 기능 추가 | `feat(game): 서랍 암호 입력 기능 추가` |
| `fix` | 잘못된 동작 수정 | `fix(record): 느린 기록이 최고 기록을 덮어쓰는 문제 수정` |
| `docs` | 문서만 변경 | `docs: PR 및 커밋 규칙 추가` |
| `refactor` | 동작은 같고 코드 구조만 변경 | `refactor(auth): 로그인 검증 책임 분리` |
| `test` | 테스트만 추가·수정 | `test(game): 열쇠 미선택 탈출 검증 추가` |
| `chore` | 기능·버그·문서·테스트 외의 유지 작업 | `chore: Git 제외 파일 설정` |
| `build` | 빌드 도구·의존성 변경 | `build: SQLite JDBC 의존성 추가` |
| `ci` | 자동 검증 설정 변경 | `ci: Java 컴파일 검사 추가` |
| `style` | 동작에 영향 없는 공백·서식 수정 | `style: 들여쓰기 정리` |

범위는 `auth`, `map`, `game`, `room`, `inventory`, `puzzle`, `record`, `db`, `app`처럼 실제 담당 기능을 쓴다. 억지로 범위를 만들 필요는 없다. 하나의 커밋에 서로 다른 목적의 변경을 섞지 않는다.

```text
# 좋은 예
feat(auth): 로그인 화면 추가
fix(puzzle): 3×3 입력에서 앞자리 0이 사라지는 문제 수정
docs: 클래스 다이어그램 사용법 추가

# 피할 예
fix: 수정
update: 이것저것 변경
feat: 로그인과 DB와 방 그래픽 모두 구현
```

기존에 쓰던 호출 방식이나 데이터 형식이 깨지는 변경은 제목의 `!` 또는 본문의 `BREAKING CHANGE:`로 표시하고, 영향을 받는 팀원에게 PR 설명에서 변경 방법을 알린다. 예: `refactor(game)!: 게임 결과 API 변경`. 본문을 쓰면 제목 다음에 빈 줄을 둔다. 이 표시는 필요한 경우에만 사용한다.

## 2. 브랜치와 PR 제목

- 브랜치는 'dev'에서 만들고 'main'으로 병합한다.

## 3. PR 본문

아래 세 항목을 기본으로 적는다. 항목에 해당하는 것이 없으면 `없음` 또는 `미실행(사유)`이라고 적는다. 화면 변경은 스크린샷이나 짧은 화면 녹화를 첨부하면 좋다.

```md
## 변경 내용
- 무엇이 바뀌었는지와 사용자가 확인할 동작

## 확인 방법
- 실행한 명령 또는 수동 확인 순서와 결과

## 참고 사항
- 관련 이슈, 함께 바뀌어야 할 계약, 남은 제약
```

예를 들어 `fix(record): 최고 기록 갱신 조건 수정` PR이라면 “기존 120초 기록이 있을 때 150초로 다시 탈출해도 120초가 유지된다”처럼 **변경 전후를 검증할 수 있게** 적는다. 실행 가능한 Java 앱과 빌드 설정이 생기기 전에는 존재하지 않는 테스트 명령을 적지 않는다.
